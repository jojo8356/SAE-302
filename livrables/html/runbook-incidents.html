Runbook — Réponse aux incidents en production (MiniShop)

Propriétaire : Astreinte Niveau 2 MiniShop · Objectif : Rétablir le service avant de chercher à embellir le diagnostic

Pendant l’incident (à chaud) : conserver l’heure UTC exacte et les journaux périssables (var/journal/*.jsonl, mariadb, Apache/PHP). Après stabilisation, si un critère de guide-postmortem-blameless.md est atteint (indisponibilité > 15–30 min, perte de données, faille sécurité ou near miss), ouvrir un postmortem sans blâme via python3 scripts/nouveau_postmortem.py.

Scénario 1 — Erreurs HTTP 500 généralisées (panne MariaDB ou identifiants .env)

  1. Vérifier l’état du service MariaDB et les connexions actives : bash systemctl status mariadb --no-pager journalctl -u mariadb -n 50 --no-pager
  2. Contrôler la configuration .env (sans jamais afficher les secrets dans un ticket ou un log) : vérifier STORAGE_DRIVER=sql, DB_HOST, DB_PORT, DB_NAME (app/Config/Database.php).
  3. Vérifier l’espace disque et les verrous InnoDB : bash df -h /var/lib/mysql /var mariadb -e "SHOW ENGINE INNODB STATUS\G" | head -n 40
  4. Si MariaDB a redémarré : vérifier le maintien des 18 procédures et 16 déclencheurs via php scripts/run-all-tests.php --sans-e2e sur la base de test (jamais sur la base client de production).

Scénario 2 — Ralentissement anormal (p95 > 200 ms)

  1. Identifier la couche coupable : consulter les métriques de latence HTTP vs temps SQL (Slow Query Log MariaDB long_query_time = 0.05, § 3.7).
  2. Vérifier les processus PHP-FPM / Apache et la saturation mémoire (free -m, top -b -n1 | head -n 20).
  3. Appliquer le repli immédiat : activer le cache HTTP/bordure sur les pages publiques catalogue (GET /, GET /catalogue, § 4.1.8) et vérifier l’absence d’un script de volumétrie ou de nettoyage concurrent.

Scénario 3 — Verrouillage administrateur (ou panne IdP cible V2)

  1. En V1 (auth locale dans administrateur) : vérifier que le compte SUPER est actif (actif = 1 en base), sans couper le trafic client, puis utiliser Auth::verifierAdmin() via l’accès d’administration sécurisé.
  2. En cible V2 (sso.minishop.fr / OIDC) : ne pas couper les clients porteurs de jetons valides et basculer sur le compte de secours (break-glass) hors IdP via bastion/VPN (§ 4.1.13).
  3. Après rétablissement : renouveler les secrets utilisés pendant l’urgence et ouvrir obligatoirement un postmortem blameless (postmortem-modele.md).

Scénario 4 — Journaux muets ou défaillance de supervision

  1. Vérifier si la boutique sert toujours : tester curl -I https://minishop.fr/catalogue (ou l’URL locale configurée).
  2. Vérifier les journaux locaux V1 (var/journal/db.jsonl, var/journal/contact.jsonl, permissions d’écriture et espace disque sous var/) ainsi que la rotation par App\Service\NettoyageJournaux.
  3. En cible V2 avec collecteur externe (OpenTelemetry Collector / Fluent Bit) : vérifier le tampon disque sans redémarrer aveuglément front-web (pipeline non bloquant, § 6.1.1), puis ouvrir un postmortem blameless pour combler l’angle mort de détection.
