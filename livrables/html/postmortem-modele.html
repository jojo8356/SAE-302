Modèle de postmortem sans blâme (Blameless Postmortem) — MiniShop

Identifiant incident : INC-AAAA-MM-JJ-01 · Date : AAAA-MM-JJ · Responsable rédaction : Nom
Règle d’or : On cherche les défaillances de système, de documentation ou d’alerte — jamais un coupable humain.

1. Résumé exécutif

  • Service touché : (front-web / admin-web / mariadb / observabilité)
  • Durée totale d’impact : HH:MM UTC → HH:MM UTC (X min)
  • Impact utilisateur : (ex. impossibilité de valider une commande ; consultation catalogue intacte)
  • Détection : (alerte métrique / watchdog / signalement client)

2. Chronologie exacte (heure UTC)

Heure UTC Événement ou action observée
HH:MM Début probable de l’anomalie (signal métrique ou erreur SQL)
HH:MM Déclenchement alerte / prise en charge astreinte
HH:MM Action de contournement appliquée (runbook-incidents.md)
HH:MM Retour vérifié à l’état nominal (p95 et taux 5xx normaux)

3. Cause racine et facteurs aggravants

  • Cause technique directe : (ex. saturation disque /var/lib/mysql, migration non testée, clé JWKS expirée)
  • Pourquoi l’incident n’a-t-il pas été stoppé avant ? (test manquant, alerte absente, runbook obsolète)

4. Plan d’actions correctives (avec propriétaire et échéance)

Action concrète Type Propriétaire Échéance Statut
Ajouter un test de non-régression ou une alerte dédiée Prévention À désigner J+7 [ ]
Mettre à jour le runbook et l’ADR impacté dans Git Documentation À désigner J+3 [ ]
