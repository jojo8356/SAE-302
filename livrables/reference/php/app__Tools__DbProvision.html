DbProvision

Description

MiniShop — création du compte MySQL applicatif (outil de développement). Pourquoi cette classe existe : sous Debian/Ubuntu, `mariadb-server` crée `root@localhost` avec le greffon `unix_socket`. Ce greffon ne compare PAS un mot de passe : il autorise la connexion quand le **processus qui se connecte tourne sous le même utilisateur du système** que le compte. Conséquences : sudo mariadb ✅ (le shell est root) php scripts/… ❌ (PHP tourne sous « jojokes ») → [1698] Access denied Aucun repli côté PHP ne peut contourner cela — c'est une décision du SGBD. La seule solution propre est donc un compte dédié, créé une fois, par un `sudo mariadb` ponctuel. C'est exactement ce que fait cette classe : 1. elle génère un mot de passe aléatoire (hexadécimal : rien à échapper) ; 2. elle écrit les CREATE USER / GRANT dans un fichier temporaire (0600) ; 3. elle l'exécute avec `sudo mariadb < fichier` ; 4. `scripts/db_init.php --compte` reporte les identifiants dans `.env`. Le compte est restreint à la base du projet (`GRANT … ON base.*`), jamais global. Deux hôtes sont créés (`localhost` et `127.0.0.1`) car MariaDB les distingue : PHP en TCP arrive en `127.0.0.1`, mais `localhost` reste utile pour les outils en socket.

public static function contexteDeTest(): bool

Une suite de tests ne doit jamais provisionner le système.

Incident réel : une vérification unitaire appelait `creerCompte()` pour
constater l'échec en l'absence de client SQL. Sur une machine où le client
existe, elle a exécuté un vrai `sudo mariadb` : le mot de passe du compte
applicatif a été remplacé par une valeur aléatoire écrite nulle part, et
toutes les connexions PDO suivantes ont échoué en `1045`.

Le garde-fou rend l'accident impossible même si un futur test se trompe :
`MINISHOP_TESTS=1` (posé par les suites et par les exécuteurs) suffit à
refuser toute création de compte ou de base.
