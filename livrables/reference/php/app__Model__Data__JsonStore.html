JsonStore

Description

MiniShop — pilote JSON secondaire (StorageDriver::JSON, choisi explicitement). « Moteur intelligent » : ce pilote reproduit, en opérations JSON natives, tout ce que le schéma MySQL du projet attend d'un SGBD — sans UNE SEULE requête SQL. En particulier : - TABLES : une table = un fichier data/minishop/<table>.json, chargement paresseux, écriture atomique (tmp + rename) ; - SCHEMA : valeurs par défaut, coercition de types, NOT NULL, ENUM, UNIQUE, CHECK, FK RESTRICT/CASCADE (cf. Schema) ; - DÉCLENCHEURS: les 16 triggers métier de sql/03 portés en callbacks PHP (cf. Triggers) — ils sont la dernière barrière, y compris pour un code applicatif défaillant (défense en profondeur) ; - TRANSACTIONS: verrou coopératif local, écritures différées, rollback avant commit ; le commit reste atomique par fichier seul. - INDEX : index PK en table de hachage (accès O(1) par clé) ; - JOURNAL : piste d'audit append-only de chaque écriture (var/journal/db.jsonl, exigence EF-GEN-04) ; - ACTEUR : setActor() mémorise qui écrit (client/admin/système) pour la piste d'audit automatique des statuts (RB-11). Les lectures (select/findOne/count/sum/exists) évaluent les conditions déclaratives ligne à ligne : le volume cible (200 produits, 1 000 commandes, cf. ENF-01/02) tient en mémoire et l'opération reste en O(n) natif. Le pilote SQL est le défaut applicatif ; ce moteur reste disponible pour les tests portables et les démonstrations sans serveur. Hors transaction, chaque écriture utilise une transaction implicite. Les processus qui modifient les fichiers sans ce store ne respectent pas ce verrou. En cas de panne pendant le commit de plusieurs fichiers, une partie du commit peut être persistée : ce stockage n'est pas un SGBD transactionnel.
